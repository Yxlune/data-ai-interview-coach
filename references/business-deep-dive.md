# 业务深挖

进入业务深挖模式时与 `question-engine.md` 一起读取。目标是验证项目为什么值得做、用户实际推动了什么，以及结果如何影响业务，而不是要求所有项目套用固定商业术语。

## 业务证据链

根据当前回答选择尚缺的相邻层，不必机械按顺序提问：

```text
场景与对象
  → 直接触发原因
  → 根本问题
  → 目标与优先级
  → 用户职责和决策边界
  → 关键动作与协作
  → 落地困难和解决方案
  → 结果、测量与归因
  → 成本、风险与业务价值
  → 复盘与可迁移经验
```

## 关键维度

### 原因与目标

确认需求由谁提出、直接原因是什么、不做会怎样、真正受影响的人是谁，以及目标是否可衡量。区分表面需求和根本问题，但不要强迫每个学术项目虚构商业需求。

### 优先级

当用户说项目“很重要”时，追问它与其他需求相比为何优先。可考察影响范围、紧迫性、战略相关性、依赖关系、成本和机会成本。

### 个人贡献

把“我们”拆成团队动作和用户动作，确认：

- 用户亲自执行了哪些环节；
- 哪些判断由用户提出或推动；
- 哪些成果依赖他人；
- 没有用户时项目是否仍会以相同方式完成。

不能因为用户参与项目就把团队成果全部归为个人贡献。

### 落地与协作

确认卡在哪一环、为什么难、涉及哪些角色、如何达成一致，以及方案是否真正投入使用。学术项目可以将“落地”解释为实验完成、方法复现、论文产出或研究决策，不虚构生产上线。

### 结果与价值

优先确认与项目目标直接相关的指标。至少区分：

- 技术指标与业务指标；
- 过程指标与结果指标；
- 一次性收益与持续收益；
- 相关性与可归因影响；
- 估算值与真实测量值。

无法量化时可以使用定性证据，但必须说明来源、范围和限制。

### 成本与负向影响

在用户只谈收益时考虑：人力、时间、计算成本、维护负担、资源挤占、误伤、隐私、公平性、合作方阻力和长期债务。只追问与当前项目真实相关的盲区。

### 复盘

确认哪些判断有效、哪里没有达到预期、重来会改变什么，以及经验能否迁移到新场景。复盘不是要求用户贬低项目。

## 常见回答的下一问方向

| 用户表达 | 优先识别的缺口 |
|---|---|
| “业务方提出了需求” | 谁受影响、为何此时提出 |
| “我负责模型部分” | 具体步骤与决策边界 |
| “推动了跨团队协作” | 分歧、用户动作与结果 |
| “效率提升了” | 指标口径或测量方式 |
| “准确率提升 5%” | 基线、数据集、业务意义与归因 |
| “项目上线了” | 使用范围、稳定性和实际采用 |
| “没有业务指标” | 可验证的替代证据及限制 |

表格用于识别方向，不得把右栏全部变成一轮多问。

## 挖透标准

业务线索只有在以下内容清楚时才可关闭：

- 原因和目标；
- 用户个人贡献与边界；
- 至少一个可验证结果或明确的证据限制；
- 结果与目标之间的关系；
- 一个真实困难及解决过程；
- 有意义的复盘。
